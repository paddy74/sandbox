# 07: Objection prep

Purpose: short, honest answers (20-30 seconds spoken) to the pushback each audience will raise on cost, complexity, trust in the data, AI reliability, security/ATO and competition, with a proof point from the demo and a "don't say" trap. Facts match files 02 and 03 (thresholds 0.9 / 0.5, `COPY INTO`, no Splink / GraphFrames / Vector Search, model registration and Genie / Apps unverified on the workspace, all demo numbers synthetic).

Retrieval date for every source in this file: **2026-10-02**. Pages were fetched with a tool that summarises the page, so open the primary page once before the demo and re-check anything dated (docs change monthly).

## 0. Rules of the road

1. **Say what ran, say what did not.** The demo ran on Databricks Free Edition with mocked sources and synthetic data. Free Edition has "no compliance enforcement" and is not covered by an SLA or for commercial use ([docs](https://docs.databricks.com/aws/en/getting-started/free-edition-limitations)). Nothing in the demo is an authorization claim.
2. **Never quote an authorization from memory.** Use only the wording in Section 5, and only for the cloud and offering named.
3. **Synthetic numbers are labelled synthetic.** Precision, REVIEW counts and "observations recovered" come from `true_object_id` simulating adjudications. They say nothing about real-world accuracy. Use the measured metrics in file 02.
4. **Competitors: trade-offs, not attacks.** State what each does well, then where the choice differs. Offer coexistence where true.
5. **Unknown is a valid answer.** "I do not know; here is the test that settles it, and I will have it for you in X" beats a guess.

## 1. Business Leader

Cares about: decision speed, one trusted number, cost of inaction, time to value, "will analysts trust it".

### 1.1 Cost: "What does this cost, and what do I get for it?"
- **Likely wording:** "This sounds expensive. Why not hire two more analysts?"
- **Answer (~25 s):** "I will not quote production pricing from a free workspace, because it would be made up. What I can say is that the whole demo pipeline took about five minutes of compute, so the cost is people-time and licences, not machine-time. The value case is analyst hours spent correlating and the cost of a wrong object count in a brief. In the 30-day plan we measure both on your data before you commit to more."
- **Proof point:** the pipeline notebook runs end to end in about 4.8 minutes of compute (file 02); the 30-day plan ends with a measured baseline versus pilot.
- **Don't say:** any dollar figure, "it pays for itself", "cheaper than Palantir / Snowflake", or an ROI percentage. Do not invent time-saved statistics.
- **Honest limit:** Free Edition cost behaviour does not predict production cost. A pilot with usage tracking is the real answer.

### 1.2 Value: "How is this different from the dashboards we have?"
- **Likely wording:** "We have dashboards. Why does a model matter?"
- **Answer (~25 s):** "A dashboard shows the count you already have. This asks the harder question: are those 10 observations 4 objects or 7? The model scores every observation against known objects. Above 0.9 it auto-associates, between 0.5 and 0.9 an analyst decides, and below that it proposes a new object. The analyst's decision is saved and becomes training data, so the system improves."
- **Proof point:** hero B (twin Trucks, review case, approve/reject writes back via MERGE) and hero C (three individually unusable observations that together become one nominated object).
- **Don't say:** "it replaces analysts" or "it finds the true count". It reduces manual correlation and surfaces ambiguity. The 0.9 / 0.5 thresholds are demo values, not tuned.

### 1.3 Trust: "Whose number is right?"
- **Likely wording:** "Every brief starts with a debate. Will this end it?"
- **Answer (~25 s):** "It makes the debate shorter and evidence-based. Each object count traces back to source observations with `source_file` and `ingested_at`, each match has a probability and a reason, and each analyst decision is recorded. You are still arguing, but about a specific uncertain case, not about whose spreadsheet is right."
- **Proof point:** `source_file` / `ingested_at` on every bronze table; `review_decisions` table; object count before and after the twin duplicates are resolved (seeded duplicates, synthetic).
- **Don't say:** "single source of truth" as a guarantee. Say "a governed, traceable source".

### 1.4 AI reliability: "Will the AI make things up in a brief?"
- **Likely wording:** "I cannot have a model inventing facts about an object."
- **Answer (~25 s):** "The dossier is only allowed to use the observations, scores and reports retrieved from governed tables, and it must cite their IDs. The demo checks that every cited ID exists in what was retrieved. It never changes object data. The analyst approves. That reduces the risk; it does not remove it, so we would test it on your reports first."
- **Proof point:** prompt restricted to retrieved rows with bracketed IDs, plus the cited-ID existence check (file 02, Layer 3).
- **Don't say:** "no hallucinations", "grounded so it is always right", or any accuracy figure.

### 1.5 Complexity: "Is this one more tool for my people to learn?"
- **Answer (~20 s):** "The analyst sees one screen: map, object, probability and why, dossier, approve or reject. The platform pieces underneath are the same workspace and the same governed tables. In the demo build I kept the parts deliberately simple, so each can be explained in one sentence."
- **Proof point:** one-screen flow (file 02, Layer 4). Be ready to say whether the app is deployed; the fallback path is notebook + dashboard + Genie.
- **Don't say:** "no training needed".

### 1.6 Competition: "We already have Palantir (or Snowflake, or AWS)."
- **Answer (~25 s):** "That is a legitimate position, and I would not ask you to rip anything out. The question for a pilot is where observation-to-object correlation and the ML sit, and whether the data stays in open formats you control. This can run alongside what you have; the first step is mapping what already holds your objects."
- **Don't say:** "they are a black box", "we are cheaper", "you are locked in". See Section 4 for factual positioning.

## 2. CDO / Data Leadership

Cares about: governance, lineage, data quality, ontology and interoperability, access control, measurable model quality, who owns the thresholds.

### 2.1 Trust in the data: "How do I know the numbers are right? Where is lineage and data quality?"
- **Likely wording:** "Show me lineage and quality. Demos always look clean."
- **Answer (~30 s):** "Demo data is synthetic and was generated clean, so I will not claim quality from it. What I built is the audit trail: every record carries `source_file` and `ingested_at`, with bronze, silver and gold layers in Unity Catalog. In production I would add expectations on the bronze tables, a quarantine for bad rows, and the lineage graph. I will show the lineage view only if it renders on this workspace; otherwise I will describe it."
- **Proof point:** `COPY INTO` idempotency (re-run adds no rows); bronze lineage columns; seeded 5% isolated noise observations that stay `NOMINATE` and do not cluster (shows no over-merging).
- **Don't say:** "data quality is solved". Lineage graph, data-quality expectations and federation to real Postgres / MySQL were not demonstrated; do not claim they ran.

### 2.2 Ontology: "Why CCO / BFO, and is it real alignment or labels?"
- **Answer (~25 s):** "The type compatibility rule reads the CCO class hierarchy loaded from the public file, so a generic Vehicle observation is compatible with Truck or Armored Fighting Vehicle through the ontology, not a hand-built list. I renamed my labels to CCO-native classes so the claim is true, not just CCO-flavoured. I am using public ontologies, not claiming a particular agency's model."
- **Proof point:** `cco_classes.ancestor_iris` drives `type_score` (file 03); IRIs verified against the local `.ttl`; hand-built taxonomy kept only as a fallback.
- **Don't say:** anything not in the "Ontology claims check" safe wording (Section 7). No event IRIs (not verified).
- **Honest limit:** no reasoning or SPARQL; ancestor lookup in a Delta table only.

### 2.3 AI reliability and model governance: "How is the model monitored and who owns the thresholds?"
- **Answer (~30 s):** "The model is a gradient boosting classifier logged in MLflow. What matters operationally is the share of auto-associations, the review volume and the reject rate in the queue. If analysts reject a lot of what the model auto-approves, thresholds tighten. Thresholds are a business decision: the cost of a false merge versus a false split, set with your analysts. Mine are demo values."
- **Proof point:** `review_decisions` become new labels for `silver_candidate_pairs`; a rules baseline can be built to compare against (file 03).
- **Don't say:** "it retrains automatically" (a retrain was described, not run unless it was), "it is 9x% accurate", or "calibrated" without a measured calibration check.
- **Honest limit:** labels come from `true_object_id` simulating adjudications; precision is synthetic.

### 2.4 Security and access control: "How are markings and access enforced?"
- **Answer (~25 s):** "A Unity Catalog row filter on a `marking` column limits which rows a user sees. In the demo that is OPEN versus RESTRICTED, deliberately not real banners. On a single-user workspace I cannot show two people seeing different rows, so I show the function and the column. Production would use attribute-based policies and audit logs, and I would confirm exactly which of those are available in your environment first."
- **Proof point:** row filter DDL checked by the feasibility notebook; ~20% of objects marked RESTRICTED (file 03).
- **Don't say:** "classified-ready" or "enforces need-to-know". Cross-domain, classification handling and which governance features exist in a GovCloud workspace are unverified (Section 5).

### 2.5 Competition: "We have data in Snowflake / a native cloud lake already."
- **Answer (~25 s):** "That data does not have to move on day one. The question is where governed access, ML and the analyst workflow run. Options are federate or share what you have, or land it here. I would test with one object type and decide on evidence."
- **Proof point:** the pipeline is the same regardless of source; mocked Postgres / MySQL show the pattern, federation untested on Free Edition.
- **Don't say:** claim any specific federation or sharing connector works with their stack without checking.

### 2.6 Cost / complexity: "Who maintains this?"
- **Answer (~20 s):** "Each component is standard and replaceable: SQL, a scikit-learn model, a table of ontology classes. I avoided specialist tools such as Splink and GraphFrames on purpose, so a small team can own it. At volume, some pieces need hardening: label propagation moves to a graph library and ingestion moves to continuous."
- **Proof point:** trade-off table in file 02 (each row has a production path).

## 3. VP / Director of Engineering

Cares about: architecture honesty, maintainability, CI/CD, scale, lock-in, security boundary, "what breaks".

### 3.1 Complexity: "Why this stack? Why `COPY INTO`, not Auto Loader?"
- **Answer (~25 s):** "`COPY INTO` is incremental and idempotent with no streaming query or checkpoint to babysit. Auto Loader hung on Free Edition serverless in my testing, so I used the thing that worked. For production, continuous ingestion with schema evolution is the right path and I would move to it."
- **Proof point:** feasibility notebook, section 2: `COPY INTO` batch, incremental and idempotent; Auto Loader is an optional check because it hit a hard 5-minute timeout.
- **Don't say:** "Auto Loader does not work" in general. It hung in this environment.

### 3.2 Scale: "H3 and SQL label propagation will not scale."
- **Answer (~25 s):** "Correct for a demo-sized set. H3 blocking cuts the pair space, and label propagation ran in seconds on the few hundred unmatched observations here. At volume I would tune the H3 resolution per object class and swap label propagation for a connected-components library. I have not tested either at scale."
- **Proof point:** trade-off table (blocking misses matches beyond the ring; resolution is a tuning choice).
- **Don't say:** any throughput or scale figure.

### 3.3 AI reliability / testing: "How do you test a model and an LLM dossier?"
- **Answer (~30 s):** "Model: precision per decision band against held-out labels, and, if built, a rules baseline. Dossier: a deterministic check that every cited ID exists in the retrieved set, plus a template-based fallback if the endpoint is unavailable. `true_object_id` is never a feature or in the prompt; I check that."
- **Proof point:** `precision_vs_synthetic_truth` printed by the pipeline notebook; ID existence check; fallback dossier (file 02, flags table).
- **Don't say:** "the model is validated". Train/test discipline and real-world accuracy are not established on synthetic data.

### 3.4 Platform limits: "Will it run in our (GovCloud / IL5) environment?"
- **Answer (~30 s):** "Not as built, and I want to be precise. I built on Free Edition, which is not a compliant environment. Some things I used are listed as unavailable on AWS GovCloud in the docs today, notably AI Functions, which includes `ai_query`, and serverless is in preview there. The pipeline logic carries over; the dossier would call a model serving endpoint directly, and I would verify model availability with the Databricks account team before committing."
- **Proof point:** Section 5 rows V11 and F3-F6 (sourced). Have the template dossier ready.
- **Don't say:** "it runs in GovCloud", "Genie / Apps / `ai_query` work at IL5", or name a specific model as available at IL5 (see V10).

### 3.5 Lock-in: "What am I locked into?"
- **Answer (~25 s):** "The logic is SQL and a scikit-learn model, and the ontology is the public CCO file; all of it is portable. What you buy in is the governed platform: Unity Catalog, MLflow, serving. I would not claim zero switching cost. I would show you which parts are portable and which are not."
- **Don't say:** "no lock-in", or any statement about table-format portability not checked on the day.

### 3.6 Competition: "Why not native AWS (Glue, SageMaker, Bedrock)?"
- **Answer (~25 s):** "A native build is a valid path and has strong authorizations. The trade-off is assembly: you integrate and govern separate services yourselves. The case for one platform is a single governance layer across data, model and GenAI. If your team already runs that AWS stack well, the pilot should compare the two on the same 30 days."
- **Proof point:** AWS Bedrock FedRAMP High and IL4/5 in GovCloud (C3, Section 6) is real; do not minimise it.
- **Don't say:** "AWS is harder", "fewer services means fewer ATO issues" (unproven).
